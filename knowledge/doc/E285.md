## 场景

OHOS PC / 无真实音频设备、无 ALSA/PulseAudio/PipeWire 等后端依赖的环境下，适配 OpenAL 类音频库（CMake 构建、后端可选项）时：

1. 默认开启的外部音频后端会因缺少依赖/设备而失败，需要显式关闭；
2. 上游测试（gtest）与运行验证依赖真实设备，无法直接执行，需要可复现的替代验证；
3. 替代验证与上游 ctest 必须分开统计，不得互相覆盖。

## 方法

### 1. CMake 关闭外部音频后端，仅保留 Null/loopback

openal-soft 1.25.2 中 `loopback.cpp` / `null.cpp` 为"Default backends, always available"（CMakeLists.txt 注释），始终编译；外部后端均有独立关闭选项：

```bash
cmake -S . -B build-tests -DALSOFT_TESTS=ON -DALSOFT_UTILS=OFF -DALSOFT_EXAMPLES=OFF \
  -DALSOFT_DLOPEN=OFF -DALSOFT_ENABLE_MODULES=OFF -DALSOFT_BACKEND_WAVE=OFF \
  -DALSOFT_BACKEND_ALSA=OFF -DALSOFT_BACKEND_PULSEAUDIO=OFF -DALSOFT_BACKEND_PIPEWIRE=OFF \
  -DALSOFT_BACKEND_JACK=OFF -DALSOFT_BACKEND_OSS=OFF -DALSOFT_BACKEND_SOLARIS=OFF \
  -DALSOFT_BACKEND_SNDIO=OFF -DALSOFT_BACKEND_PORTAUDIO=OFF \
  -DALSOFT_BACKEND_SDL2=OFF -DALSOFT_BACKEND_SDL3=OFF
```

实测 `config_backends.h`：ALSA/OSS/PipeWire/Solaris/SndIO/PortAudio/PulseAudio/JACK/CoreAudio/OpenSL/Oboe/Wave/SDL3/SDL2 均为 0，构建日志 "Building OpenAL with support for the following backends: Null"。最小核心构建 `cmake --build build-min -j4` rc=0，产物 `libopenal.so`（1,833,472 字节）。

### 2. 无真实设备时使用 `No Output` null 后端

`alcOpenDevice("No Output")` 即可打开内置 null 后端（设备名 "OpenAL Soft"），无需任何硬件/外部库；随后 `alcCreateContext` 可正常创建上下文。

### 3. 使用 `ALC_SOFT_loopback`、context 属性列表和 `alcRenderSamplesSOFT`

注意：openal-soft 1.25.2 **没有 `alcSetFormat`**；loopback 格式通过 `alcCreateContext` 的属性列表设置（`ALC_FORMAT_CHANNELS_SOFT` / `ALC_FORMAT_TYPE_SOFT` / `ALC_FREQUENCY`，见 alc.cpp `UpdateDeviceParams`）：

```bash
clang++ -std=c++20 openal-probe-verify.cpp -I include -L build-tests -lopenal -o openal-probe-verify
LD_LIBRARY_PATH=build-tests ./openal-probe-verify
```

实测输出（临时程序，未修改上游测试）：`No Output` 打开成功、`ALC_SOFT_loopback` 扩展存在、`alcLoopbackOpenDeviceSOFT` 成功、`alcCreateContext` 接受 stereo/16bit/48k、`alcRenderSamplesSOFT` 渲染 960 samples 无错误；退出码 0，失败数 0。

### 4. 上游 ctest 与替代验证分开统计

- 上游：`ctest --test-dir build-tests --output-on-failure -V` → 退出码 0，发现 1 个（ExampleTest.Basic），通过 1、失败 0，通过率 **1/1（100%）**。
- 替代：上述临时程序独立统计（0 失败），两者互不覆盖。
- 注明：测试构建使用了离线 GoogleTest 与 `-DATOMCODE_PROBE_FORCE_FMT`，属 OHOS 探针 workaround 下的结果。

### 5. `sign-elf` 缺失、libc++ workaround 和适用边界

- 环境实测 `sign-elf` 不存在；因此上述运行结果只能作为**探针证据**，不能作为可交付 ELF 的完整门禁证据（正式交付仍需 sign-elf 或等价签名流程）。
- OHOS SDK libc++ 15.0.4 缺少部分 `<ranges>` 视图（`views::elements`、`views::split`）、`<source_location>`、`<format>`（`std::format_error` 未导出）等能力；Clang 15 还触发结构化绑定捕获、`typename` 缺失、P0960 括号聚合初始化等兼容问题。均为**本地探针修复**（`-D_LIBCPP_ENABLE_EXPERIMENTAL` + `$HOME/tmp/compat-inc` shim 头 + 少量 init-capture/typename/花括号等价改写），**未形成仓库 patch**。
- 补丁归类（本轮收口）：8 个编译修复补丁为**探针临时材料**，已移出正式归档至 `$HOME/tmp/openal-1.25.2-reports/probe-patches/patches/`；`conandata.yml` 仅保留官方 GitHub URL（无镜像、无 file://），`conanfile.py` 无绝对临时路径依赖；**正式配方当前不可复现**（干净 OHOS 工具链 conan create 失败，首个错误 `std::lexicographical_compare_three_way` 缺失），需先形成可审查正式 patch 并复核 ABI 影响。
- 适用边界：这些 workaround 仅适用于探针验证阶段；正式适配若需在 OHOS 工具链上交付，应按仓库补丁管线沉淀为可审查 patch，并复核 libc++ 能力差异的 ABI 影响。
- 普通 libc++/Clang 编译修复、fmt workaround（`-DATOMCODE_PROBE_FORCE_FMT`）、GoogleTest 离线接入（`FETCHCONTENT_SOURCE_DIR_GOOGLETEST`）**不作为路径 B 主证据**；路径 B 的证据是本条目的 null/loopback + 无设备替代验证可复用方法。

## 依赖情况

- fmt-11.2.0、gsl：源码内置（`add_subdirectory(fmt-11.2.0 EXCLUDE_FROM_ALL)`；gsl 纯头文件，无独立目标）。
- Threads：`find_package(Threads)`，系统线程基础能力。
- GoogleTest：FetchContent 外部依赖（`GIT_TAG main`），实际解析 commit `1b6f64d659944658a4c685b7bd9f04c1c3b8a39b`，**不是零依赖**。
