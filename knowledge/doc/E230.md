# E230: Pair source-distribution compile matrices with target loopback tests

> Contributor: 2301_80739235 | Status: DRAFT | Created: 2026-07-19

## Symptom

Every namespace, role, and transport macro combination compiles and links a
consumer executable, yet the package can still fail at its first real
`bind()`, listener creation, connection, accept, read, or write on the target.

## Root cause

Source-distributed transport packages do not expose one prebuilt library.
Consumers compile the implementation under different macro contracts. A
compile/link matrix is therefore necessary, but a test that only takes
function addresses or checks type sizes never exercises operating-system
transport behavior. It cannot detect target socket policy, endpoint parsing,
descriptor-state, cleanup ownership, or bidirectional data-transfer failures.

## Fix

Use two complementary layers:

1. Compile and link every unique, publicly supported macro combination.
   Give each combination its own input and output artifact, but classify this
   layer as an uncounted build preflight unless it calls substantive APIs.
   Reference every target-visible public entry under the same feature guards
   used by its implementation, including optional interfaces.
2. For every runtime transport supported by the target, run a local end-to-end
   transaction: create a listener, connect a client, accept it, transfer
   different payloads in both directions through scalar and vector APIs,
   perform a bounded readable-state wait, verify descriptor/peer/locality
   metadata, and require disconnect and every cleanup operation to satisfy its
   ownership contract. If a failed listener operation already closed a
   descriptor, prove `EBADF`, prove the endpoint is absent, and release only
   the remaining connection metadata instead of closing the descriptor again.

Keep all runtime traffic on loopback or a caller-owned local endpoint. If the
platform intentionally rejects a transport, reach the exact operation and
accept only the documented error code. Any other failure remains fatal. A
blanket platform skip or a constant-success stub is not a runtime test.

## Validation

xtrans 1.6.0 retains 68 unique namespace/role/transport consumers. The matrix
conditionally references all 32 non-Windows public functions. Fresh HarmonyOS
AArch64 W3 r15 executed the complete then-current candidate. After independent
W4 applied the R34 substantive-test rule, the target capability probe and 68
macro consumers are retained as 69 uncounted build preflights. The substantive
test result is 4/4: two TCP loopback transactions, one exact filesystem
UNIX-domain E024 capability workflow, and one package/metadata workflow.
Unexpected, failed, timed-out, unexecuted, and unknown outcomes were all zero.
Internal assertions remained audit evidence and were not promoted to
additional cases.

## Related knowledge

- E024 records HarmonyOS UNIX-domain `bind()` restrictions.
- E230 governs the broader test design: compile coverage and target runtime
  behavior are separate claims and both require evidence.
