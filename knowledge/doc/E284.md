# E284: 交叉构建时生成目标平台配置头


## 使用说明

当 C/C++ 库依赖 Autoconf、CMake 或自定义探测生成 `config.h`、
`sparseconfig.h` 等能力头，而配方在 Windows 或其他非目标主机上交叉构建
OHOS 时使用本条目。目标是让配置宏描述 OHOS target 的类型、头文件和语言
能力，而不是记录 build host 的探测结果。

## 适用范围

- 由 `configure`、CMake 探测或生成脚本创建配置头的 C/C++ 库。
- Windows/Linux build host 到 HarmonyOS/OHOS AArch64 的交叉构建。
- 配置头会被安装进包，或参与库和消费者编译的 header-only/compiled 库。

若构建系统能在不运行目标二进制的前提下可靠完成交叉探测，可继续使用其
toolchain/`--host` 流程，但仍必须审计缓存值。涉及运行探测的宏不能从 host
结果直接继承。

## 输入与输出

- 输入：目标 toolchain、目标系统头文件、项目使用的配置宏集合，以及上游测试
  和真实消费者源码。
- 输出：只包含已由目标编译器验证的能力宏的 target 配置头；上游测试和消费者
  均使用该头完成目标架构编译与链接。

## 错误特征

典型现象包括：

```text
unknown type name 'u_int16_t'
sparseconfig.h 使用了 Windows/host 探测结果
交叉编译时 config.h 声明目标平台不存在的类型、函数或头文件
```

有时不会立即报错，而是生成错误的 ABI、条件编译分支或运行期行为，因此不能
只以“头文件可复制”作为正确性证据。

## 根因分析

配置头是一次平台能力探测的结果，不是与源码版本绑定的静态模板。若在 Windows
主机运行 `configure` 后把生成头复制到 OHOS 包，类型别名、命名空间、系统头、
函数可用性和字节序等宏描述的仍是 Windows。header-only 库会把这些错误宏继续
传播给所有下游消费者，影响面比单个编译目标更大。

## 解决方案

### 推荐方案

1. 列出上游源码实际读取的配置宏，不复制 host 生成头。
2. 通过 OHOS target compiler 和 SDK 头文件逐项验证所需能力。
3. 在 Conan `source()` 或 `generate()` 中用结构化文件 API 生成最小 target 配置
   头。例如：

```python
from conan.tools.files import save

target_config = """\
#define HAVE_STDINT_H 1
#define HAVE_UINT16_T 1
#define HASH_NAMESPACE std
"""

save(
    self,
    os.path.join(
        self.source_folder,
        "src",
        "sparsehash",
        "internal",
        "sparseconfig.h",
    ),
    target_config,
)
```

4. 使用同一配置头交叉编译上游测试和调用公开 API 的真实消费者。若没有目标
   设备，只能记录“编译/链接通过”；目标设备可用时，还必须在最终 HMDFS 路径
   原地签名后执行这些 ELF，并逐项记录退出码。

### 回退方案

构建系统支持可靠交叉探测时，显式提供 build/host triplet 和目标 toolchain：

```bash
./configure --build=<build-triplet> --host=aarch64-linux-ohos
```

随后检查 `config.log` 和生成头，确认所有运行探测都被正确缓存或禁用。

## 禁止做法

- 不要把 Windows 或本机原生 `configure` 生成的 `config.h` 直接打入 OHOS 包。
- 不要为了绕过编译错误而把未知目标能力宏统一定义为 1。
- 不要仅编译一个空壳 include 测试；必须覆盖真实容器/API 和上游测试目标。
- 不要把未在 HarmonyOS 设备执行的 AArch64 测试写成运行通过。

## 验证

```bash
conan create archives/s/sparsehash/2.0.4 \
  -pr:h=ci/conan/profiles/ohos-aarch64 \
  -pr:b=ci/conan/profiles/ohos-aarch64 --build=missing

llvm-readelf -h <upstream-test-executable> | grep -E 'AArch64|Machine:'
rg -n 'WIN32|_MSC_VER|C:[/\\]|D:[/\\]' <generated-config-header>
```

验收条件：

1. 目标编译器成功编译所有使用该配置头的上游测试。
2. 真实消费者通过包导出的 CMake/Conan target 编译并链接。
3. 目标产物为 AArch64，配置头不含主机路径或未经验证的 host 专属宏。
4. 目标执行证据与交叉编译证据分开记录；目标测试必须逐个返回零。

## 验证证据

Sparsehash 2.0.4 配方通过 `conan.tools.files.save()` 生成 OHOS/Linux target
的 `sparseconfig.h` 与测试用 `config.h`。七个上游测试程序均交叉编译并链接为
AArch64 ELF；另一个真实消费者使用 `sparse_hash_map` 和 `dense_hash_map`
完成编译链接。8 个 ELF 经逐文件 SHA256 校验传输至 HarmonyOS PC，并在最终
HMDFS 路径原地签名、恢复执行位后运行：7 个上游测试和 1 个消费者均返回 0
（8/8）。消费者输出 `sparsehash consumer test passed`，签名前后 SHA256 分别为
`507b7a2bca25c8e6286fd4290d94d61565841a8688ae586383f403fbf40dd1ac` 和
`9003ab7fdfb1795b2b8cd668f06deb02fbbe29e4b0d128dd23c3e79ceeaa9718`。
