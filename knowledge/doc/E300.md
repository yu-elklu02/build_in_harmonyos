# E300 - Bridge Conan paths into custom CMake find modules

## Error signature

```text
Could NOT find <dependency> (missing: <DEP>_INCLUDE_DIR <DEP>_LIBRARY)
<DEP>_INCLUDE_DIR-NOTFOUND
<DEP>_LIBRARY-NOTFOUND
```

## Trigger

- Build system: CMake under a Conan recipe
- Phase: cross-configuration
- Condition: the project ships a custom `Find*.cmake` module that consumes
  legacy cache variables instead of Conan-generated targets.

## Root cause

`CMakeDeps` can generate valid config targets without satisfying an unrelated
upstream find module. During a cross build, normal system search paths are also
insufficient and may select host files. The recipe must bridge the locked Conan
package paths into the exact variables read by that module.

## Recommended solution

1. Read the upstream `Find*.cmake` implementation and identify its exact cache
   variable names.
2. Resolve the dependency through `self.dependencies`.
3. Verify that the required header and library exist inside that package.
4. Pass those exact paths through `CMakeToolchain` before `tc.generate()`.
5. Confirm `CMakeCache.txt` points to the intended Conan package revision.

For GROMACS 2026.3 mixed precision, `FindFFTW.cmake` reads
`FFTWF_INCLUDE_DIR` and `FFTWF_LIBRARY`. The OHOS target configure resolved
both values from the published `fftw3f/3.3.9` binary and continued into the
subsequent compilation phase.

## Forbidden approach

- Do not hard-code `/usr/include`, `/usr/lib`, or host paths. That bypasses the
  locked dependency and makes target configuration non-reproducible.
- Do not assume a generated Conan target is sufficient without reading the
  upstream find module.

## Verification

```text
Inspect Find*.cmake inputs -> verify package header/library -> configure ->
read CMakeCache.txt -> bind recipe revision and package ID from Conan graph.
```
