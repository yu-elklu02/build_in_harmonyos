# E306 - Negative-radius `std::polar` calls are not portable

## Symptom

A filter or geometry setup succeeds with Linux `libstdc++` but throws or
produces NaN values on HarmonyOS `libc++`. A representative failure is:

```text
libc++abi: terminating due to uncaught exception of type std::invalid_argument:
Pole to add is NaN.
```

A minimal probe makes the library difference visible:

```text
std::polar(-2.0, pi / 2) -> nan,nan
direct components        -> -1.2246467991473532e-16,-2
```

## Root Cause

The C++ contract for `std::polar(rho, theta)` requires `rho` to be non-negative
and finite. Using a negative radius to encode a sign has undefined behavior.
Some `libstdc++` versions happen to multiply the signed radius by sine and
cosine, but HarmonyOS `libc++` returns NaN components for the same input.

iir1 1.10.0 used negative `gp` and `gz` values as the radius in the
Butterworth shelf prototype. The first expanded HarmonyOS consumer case that
exercised `LowShelf<2>` therefore exposed a real library portability defect.

## Fix

Construct the intended signed complex components directly:

```cpp
addPoleZeroConjugatePairs(
    complex_t(gp * cos(theta), gp * sin(theta)),
    complex_t(gz * cos(theta), gz * sin(theta)));
```

An equivalent alternative is to make the radius positive and add pi to the
angle when the original radius is negative. Do not retain a negative radius
merely because the current host standard library appears to accept it.

## Verification

1. Run a minimal negative-radius probe with the host and target C++ libraries.
2. Replay the source patch against the official archive with zero fuzz.
3. Rebuild shared and static packages from clean source.
4. Execute the formerly failing API plus the complete consumer suite on the
   HarmonyOS PC; for iir1 this means all 46 independent consumer commands in
   each package mode.
