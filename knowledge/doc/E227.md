# E227 - Canonical unified-patch context versus outer Git whitespace checks

## Symptom

Adding or renaming a canonical `.patch` file can make the outer repository
report whitespace errors such as:

```text
patches/0002-example.patch:15: trailing whitespace.
raw line == "+<space>"
patches/0001-example.patch:33: new blank line at EOF.
```

Reading the patch blob shows that each flagged content line is exactly one
ASCII space (`raw line == " "`). The source edit itself has no trailing
whitespace, and both patch engines can still parse the patch cleanly.

## Trigger Conditions

- A canonical unified diff is added as a file inside another Git repository.
- An unchanged empty source line occurs inside a patch hunk's context range.
- The outer repository runs `git diff --check` on the `.patch` as ordinary
  text instead of interpreting its inner unified-diff grammar.

## Root Cause

Unified-diff syntax prefixes every unchanged context line with one space.
When the unchanged source line is empty, its complete representation in the
patch file is therefore a single space. An outer `git diff --check` sees that
syntax byte as trailing whitespace in a newly added text file, although it is
not trailing whitespace in the patched source.

This diagnosis is valid only after all of the following are true:

1. The actual modified source lines contain no trailing whitespace.
2. Every flagged single-space line lies inside a unified-diff hunk and denotes
   unchanged context, not added source text.
3. `git apply --check` accepts the complete patch set.
4. GNU `patch --dry-run --fuzz=0 -p1` accepts every patch against a fresh,
   checksum-verified upstream source tree.

If any condition fails, treat the report as a real patch or source defect.

## Recommended Validation

Keep ordinary whitespace validation for every non-patch change, and give
patch files parser-aware validation:

```bash
git diff "$BASE"...HEAD --check -- . ':(exclude,glob)**/*.patch'
git apply --check patches/0001-example.patch patches/0002-example.patch
patch --dry-run --fuzz=0 -p1 -d "$FRESH_SOURCE" \
  -i patches/0001-example.patch
patch --dry-run --fuzz=0 -p1 -d "$FRESH_SOURCE" \
  -i patches/0002-example.patch
```

If the repository wants one global `git diff --check` command, a separate
framework PR may narrowly configure patch-file whitespace attributes, for
example `whitespace=-blank-at-eol,-blank-at-eof`. A software recipe PR must
not introduce that framework-wide policy as an incidental workaround.

## Forbidden Workarounds

- Do not delete unrelated blank lines from upstream source merely to change
  patch context rendering.
- Do not strip the unified-diff context prefix from the generated patch.
- Do not regenerate with zero context (`n=0`); that removes placement evidence
  and weakens review even if a line-number-only patch happens to apply.
- Do not disable all whitespace checking; genuine non-patch regressions must
  remain blocking.

## Verification Evidence

JsonCpp 1.9.8 reproduced the outer-check report after both patches were
regenerated by `refresh-patch --auto` with ten context lines. The flagged
lines were all exact single-space context records. The modified source lines
had no trailing whitespace, the non-patch repository diff was clean, and the
complete patch set passed both `git apply --check` and GNU patch with
`--fuzz=0`. Fresh shared and static HarmonyOS builds then used the same recipe
revision and passed all upstream and consumer tests.

## Related Rules

- R3: patches must be generated through the patch pipeline.
- W4: independently audit patch replay and distinguish parser evidence from
  outer-container formatting checks.
