# E229: Compile-only Conan tests without CMake


## Symptom

A Conan recipe for a header-only or protocol-header package builds and packages
successfully on HarmonyOS PC, but its `test_package` fails before consuming the
package:

```text
/system/bin/sh: cmake: inaccessible or not found
ConanException: Error 127 while executing
```

## Root cause

The consumer only needs compile-only checks, but a generic
`CMakeToolchain`/`CMakeDeps` test template makes CMake an unnecessary runtime
dependency. The OHOS profile already declares the correct compiler through
`tools.build:compiler_executables`; bypassing that declaration with `CC`,
`CXX`, `cc`, or `clang` fallbacks can select a different toolchain in CI.

This pattern is limited to consumers that do not link, generate configuration
headers, run code generators, or verify exported CMake targets.

## Fix

Read the compiler exclusively from Conan configuration and fail explicitly when
the profile omits it:

```python
compiler_executables = self.conf.get(
    "tools.build:compiler_executables", default={}, check_type=dict
)
compiler = compiler_executables.get("c")
if not compiler:
    raise ConanException(
        "tools.build:compiler_executables must define the C compiler"
    )

self.run(
    f'"{compiler}" -std=c11 -Werror {include_flags} '
    f'-c "{source}" -o "{output}"'
)
```

Use a separate source and object for every genuinely independent public-header
input so each test has its own failure boundary. Keep warning policy strict;
exclude headers that intentionally emit upstream obsolescence warnings rather
than disabling `-Werror` globally.

## Do not use this pattern when

- the consumer must link against a library or its transitive dependencies;
- the package requires generated headers or code generators;
- the contract being tested is an exported CMake target;
- the only proposed test prints success without including the package; or
- the compiler comes from `CC`, `CXX`, `cc`, or `clang` instead of the profile.

Those cases require a declared, reproducible build tool and the normal Conan
toolchain/dependency integration.

## Validation

The xorgproto 2025.1 dependency recipe was run on HarmonyOS PC with a fresh
Conan home and the repository OHOS profile. CMake was absent, while the profile
provided Clang 15. The final run returned 0 and produced:

```text
validated 29 relocatable pkg-config modules
validated 83 independent public-header compile outputs
```

The package contained 156 public headers, 29 `.pc` files, and 11 protocol
documents. The upstream keysym check separately returned its documented exit-77
SKIP because Python `libevdev` was unavailable.

## Related knowledge

- E191 uses `CMAKE_TRY_COMPILE_TARGET_TYPE=STATIC_LIBRARY` when CMake exists but
  a header-only C++ configure check cannot link. E229 applies when CMake itself
  is unavailable and the consumer contract is compile-only.
