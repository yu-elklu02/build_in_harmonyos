# E231 - 官方上游测试发现未绑定已校验压缩包导致证据来源不可证明

## 问题现象与风险

自定义 runner 可能校验一个官方源码压缩包，却从另一个可指定的源码目录发现和编译测试。若 discovery-only 还能在压缩包校验前返回，动态统计和完整执行就不具备同一来源保证。压缩包本身哈希正确，不能单独证明测试实际消费了其中的字节。

## 触发条件

- runner 同时接受官方压缩包和独立 `--source` 目录。
- 压缩包校验位于测试发现之后。
- discovery-only 与完整执行走不同的来源准备路径。
- 测试清单依靠手写文件名或预测分桶，而不是从已校验来源动态生成。

## 根因

来源校验和测试消费是两个彼此独立的动作。报告记录的是压缩包哈希，测试发现与编译读取的却可能是另一棵目录；二者之间没有路径集合和逐文件内容的一一关系。

## 推荐方案

1. 在任何 discovery 前校验官方压缩包 SHA256。
2. 规范化并校验 tar 成员名，从其中的普通文件字节流直接生成相对路径、大小、逐文件 SHA256 及聚合清单哈希。
3. 在 runner 管理的新临时目录自行解包，拒绝外部源码目录参数；不在 HMDFS 上用目标 Python `rglob` 或逐文件打开生成清单。
4. discovery-only 和完整执行都只接收这棵临时解包树。
5. 测试数量仍从官方注册文件与源码动态发现；固定总数只作为版本漂移门禁，不作为发现算法。

libffi 3.5.2 的实现入口是：

```text
python archives/l/libffi/3.5.2/validate_upstream_runner.py \
  --archive <official-archive>
```

## 回退方案

若平台构建必须使用已应用补丁的源码树，则在 discovery 前动态导出 runner 实际会读取的文件闭集，再与已校验压缩包成员比较：

- 相对路径集合必须完全相等。
- 每个文件的 SHA256 必须相等。
- 缺失、增加或内容变化均立即终止。
- discovery-only 与完整执行必须复用同一比较函数。

## 禁止做法

- 手写测试文件清单、静态预测分类或按预期数量补齐输入。
- 只记录压缩包哈希，却继续接受独立源码树。
- 在来源校验前返回 discovery 结果。
- 将同一测试的优化级别、链接形态或内部断言重复计为独立入口。
