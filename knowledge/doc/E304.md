# E304 - Bound FFTW planning policy to target startup evidence

## Error signature

```text
MdrunMpi1RankPmeTests ... Timeout 600.03 sec
[ RUN      ] ReproducesEnergies/PmeTest.Runs/basic__notunepme__npme_0__pme_cpu
Using 1 MPI thread
```

The process remains CPU-active but produces no simulation progress before the
outer test timeout.

## Trigger

- Build system: CMake with an external FFTW dependency.
- Runtime: short-lived target processes that each construct fresh
  multidimensional FFT plans.
- Evidence boundary: the test input performs only a small number of simulation
  steps, while an isolated first case remains in startup for minutes.

## Root cause

FFTW planning policy is separate from transform correctness. GROMACS defaults
to `FFTW_MEASURE` unless a caller requests conservative planning. The upstream
`GMX_DISABLE_FFTW_MEASURE` option changes the primary `fft_fftw3.cpp` wrapper,
but the direct 3D planner in `fft5d.cpp` chooses from `FFT5D_NOMEASURE` instead.
That planner originally ignored the configured no-measure policy during
normal, non-reproducible runs.

On the observed OHOS AArch64 target, r6 registered all 86 CTest entries but
eight mdrun groups stopped at exactly 600 seconds. Three PME groups did not
finish even their first GTest. A separate 180-second single-case diagnostic
remained CPU-active after printing `Using 1 MPI thread`; it was not blocked on
missing test data or a CTest scheduling dependency. A fresh r7 build proved
the generated macro was `1` and accelerated some mdrun groups, but the direct
planner still selected `FFTW_MEASURE`; enabling the option alone was therefore
only a partial fix.

## Recommended solution

1. Confirm the application exposes an upstream planning-policy option.
2. Bind the option through the Conan CMake toolchain for the affected target.
3. Audit wrapper-based and direct FFTW planner paths. If a direct planner uses
   a separate flag, propagate the same configured policy at the final planner
   selection.
4. Verify the generated macro and resulting `FFTW_ESTIMATE` selection.
5. Keep the same FFT library, transforms, registered tests, and assertions.
6. Run the complete suite from a fresh build, followed by the package consumer.

The fresh r8 run validated the complete path. Its generated `config.h` defined
`GMX_DISABLE_FFTW_MEASURE` as `1`, patched `fft5d.cpp` mapped the policy to
`FFTW_ESTIMATE`, all 86 registered CTest entries passed in 29.70 seconds, and
the packaged command consumer passed 10/10 checks. The corresponding
`conan-create.log` SHA256 is
`e7f92b09ac24fc7b9244a73ebb9d6265f41a34577efea378a7ac96a01aab39be`.

## Forbidden approaches

- Do not remove PME/mdrun tests or report a filtered rerun as full coverage.
- Do not only inflate CTest timeouts without isolating whether startup planning
  dominates the test.
- Do not replace the locked FFTW dependency with a slower fallback merely to
  avoid its planner.

## Verification

```text
generated macro -> isolated first FFT-backed case -> fresh complete CTest ->
packaged command consumer -> elapsed time and log SHA-256
```

If measured plans are required for production throughput, validated
target-specific FFTW wisdom is a possible fallback, but it must be bound to the
exact CPU and FFTW package rather than reused generically.
