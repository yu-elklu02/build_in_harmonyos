# E290: CMake 类型探测不能使用 check_symbol_exists


## 使用说明

当项目把 Autoconf `AC_CHECK_TYPES` 或其他类型能力探测迁移到 CMake，且
`HAVE_*` 结果错误地显示 typedef 不存在时使用本条目。核心做法是让目标编译器
编译一段真正声明该类型的最小源码，而不是把类型当作函数、变量或宏来探测。

## 适用范围

- 使用 CMake 生成 `config.h` 或 `HAVE_*` 能力宏的 C/C++ 项目。
- 需要检测 typedef、类型别名或内核头文件类型的原生和交叉构建。
- 从 Autoconf `AC_CHECK_TYPES` 迁移到 CMake 的配方或上游构建脚本。

本条目不适用于函数、变量或预处理器宏探测；这些对象可继续使用
`check_function_exists`、`check_symbol_exists` 等对应 API。

## 输入与输出

- 输入：目标类型名、定义该类型的头文件、目标 toolchain，以及能合法引用该类型
  的最小 C/C++ 表达式。通用探测优先声明指针，避免要求类型可用整数初始化。
- 输出：由目标编译器实际编译结果生成的 `HAVE_TARGET_TYPE` 或同类缓存变量；类型
  存在且可用时为真，否则为假。

## 问题现象

典型错误写法：

```cmake
include(CheckSymbolExists)
check_symbol_exists("__kernel_rwf_t" "linux/fs.h" HAVE_KERNEL_RWF_T)
```

即使 `linux/fs.h` 已定义 `__kernel_rwf_t`，结果仍可能是：

```text
Looking for __kernel_rwf_t - not found
HAVE_KERNEL_RWF_T:INTERNAL=
```

下游表现为功能被静默禁用、`config.h` 缺少 `HAVE_*`，或相关代码随后报告
`unknown type name`。

## 根因

`check_symbol_exists` 先检查名称是否为宏；若不是宏，会生成对该名称取地址的测试
代码。typedef 只是编译期类型别名，不是函数、变量或可取地址的符号，因此该测试
对 typedef 必然失败。这是探测 API 选择错误，不是目标头文件缺失。

## 修复步骤

1. 找到上游类型定义所在的目标头文件。
2. 用 `CheckCSourceCompiles` 编写最小编译探测，声明一个该类型的变量。
3. 保持探测使用与正式构建相同的 target toolchain、sysroot 和编译标志。
4. 强制重新构建被测包，不能仅复用旧 package ID 对应的 binary。
5. 检查 CMake 输出、生成的配置头和最终消费者编译结果。

可执行示例：

```cmake
include(CheckCSourceCompiles)

check_c_source_compiles(
  "#include <linux/fs.h>
   int main(void) {
     __kernel_rwf_t value = 0;
     return (int)value;
   }"
  HAVE_KERNEL_RWF_T
)
```

这与 Autoconf 的类型探测语义对应：

```m4
AC_CHECK_TYPES([__kernel_rwf_t], [], [], [[#include <linux/fs.h>]])
```

## 禁止事项

- 不要用 `check_symbol_exists` 检测 typedef 或以 `_t` 命名的类型别名。
- 不要因为目标头文件中“看起来存在”就手工把 `HAVE_*` 固定为 1。
- 不要只导出新 recipe 后复用旧 binary；涉及配置探测的修复必须强制重建。
- 不要把交叉编译通过写成目标端运行通过。

## 验证方式

配置阶段应出现成功的编译探测：

```text
-- Performing Test HAVE_KERNEL_RWF_T
-- Performing Test HAVE_KERNEL_RWF_T - Success
```

随后检查缓存或配置头，并完成真实消费者编译：

```bash
rg -n "HAVE_KERNEL_RWF_T" build/CMakeCache.txt build/config.h
cmake --build build --verbose
```

交叉构建还应检查产物架构，并明确记录目标执行边界：

```bash
llvm-readelf -h <package-lib> | grep -E 'AArch64|Machine:'
```

## 验证证据

libev 4.33 的初始 CMake 配方用 `check_symbol_exists` 检测
`__kernel_rwf_t`，AI Review 指出该 typedef 会被稳定误判。改为编译探测后，强制
OHOS AArch64 `conan create` 日志明确显示 `HAVE_KERNEL_RWF_T - Success`；共享库
和真实消费者均重新完成交叉编译。最终制品为 AArch64 ELF64，SONAME 为
`libev.so.4`，RUNPATH 为 `$ORIGIN`。本机 `can_run=false`，未执行目标二进制。
