# E296: Complete an OHOS Meson cross file on a Windows build host

> **Severity**: medium | **Category**: Conan / Meson / Windows cross build

## Usage

Use this pattern when Conan runs on Windows and Meson cross-builds a C or C++
library for OHOS armv8. It applies when the Conan profile has valid SDK compiler
paths and a CMake OHOS user toolchain, but the generated Meson cross file lacks
the OHOS target, sysroot, or LLVM archive tools.

## Scope

- Build machine: Windows x86_64.
- Host/target: OHOS armv8 (`aarch64-linux-ohos`).
- Build system: Meson driven by Conan 2 `MesonToolchain` and `Meson`.
- SDK layout: `native/llvm/bin` and `native/sysroot` share one SDK root.

Do not apply these exact paths to native OHOS builds or a different target
architecture. Derive values from the active Conan profile rather than a user
name or fixed SDK installation directory.

## Inputs

- `tools.build:compiler_executables` containing absolute SDK `c`/`cpp` paths.
- Conan host settings `os=OHOS` and `arch=armv8`.
- The generated `conan_meson_cross.ini`.
- A package folder used as Meson's install `--destdir`.

## Outputs

- Meson uses `/` as the target prefix and keeps files staged under the Conan
  package folder.
- Compiler and linker probes target `aarch64-linux-ohos` with the SDK sysroot.
- Meson invokes absolute `llvm-ar.exe` and `llvm-ranlib.exe` paths on Windows.
- Produced libraries and test executables are AArch64 ELF files.

## Symptom And Root Cause

The first setup failure can be:

```text
ERROR: prefix value 'C:/' must be an absolute path
```

After changing only the prefix, Meson may report:

```text
ERROR: Unable to detect linker for compiler clang++.exe
clang++: error: unable to execute command: program not executable
```

The SDK compiler then identifies itself as `x86_64-w64-windows-gnu`. Conan's
Meson helper derived `C:/` from the Windows build machine. The profile's CMake
user toolchain is irrelevant to Meson, and compiler executable paths do not
implicitly select the OHOS target or sysroot.

## Implementation

Keep the correction in the recipe or a project-owned Meson machine file:

```python
import os

from conan.errors import ConanInvalidConfiguration
from conan.tools.meson import Meson, MesonToolchain


class PosixPrefixMeson(Meson):
    @property
    def _prefix(self):
        return "/"


def configure_ohos_meson(conanfile, toolchain):
    executables = conanfile.conf.get(
        "tools.build:compiler_executables", default={}, check_type=dict
    ) or {}
    compiler = executables.get("cpp") or executables.get("c") or ""
    llvm_root = os.path.dirname(os.path.dirname(compiler))
    sysroot = os.path.join(os.path.dirname(llvm_root), "sysroot")
    if not compiler or not os.path.isdir(sysroot):
        raise ConanInvalidConfiguration("OHOS SDK compiler/sysroot missing")

    flags = [
        "--target=aarch64-linux-ohos",
        "--sysroot={}".format(sysroot.replace("\", "/")),
    ]
    toolchain.c_args.extend(flags + ["-D__MUSL__"])
    toolchain.cpp_args.extend(flags + ["-D__MUSL__"])
    toolchain.c_link_args.extend(flags)
    toolchain.cpp_link_args.extend(flags)
```

After `MesonToolchain.generate()`, add the absolute SDK `llvm-ar.exe` and
`llvm-ranlib.exe` paths to `[binaries]` in the generated cross file. Use the
non-`.exe` names on non-Windows build machines.

## Forbidden Approaches

- Do not assume a CMake user toolchain affects Meson.
- Do not hardcode a user-specific SDK path in the recipe.
- Do not set only `host_machine.system = harmonyos`; that does not change the
  compiler driver's target.
- Do not use a Windows drive as the target prefix.
- Do not mark a package built after linker detection alone; force the complete
  source build and a real consumer link.

## Verification

1. Generate the cross file without compiling and inspect `[binaries]` and
   `[built-in options]`.
2. Run SDK clang with the generated target/sysroot and require linker detection
   to return the OHOS LLD driver.
3. Force `conan create --build=<package>/*`.
4. Confirm upstream target compilation and real `test_package` linkage.
5. Inspect the package and consumer with `llvm-readelf -h -d`; require AArch64
   and the expected SONAME/NEEDED entries.
6. If a HarmonyOS PC target is available, transfer the final ELF files, sign
   them in place on HMDFS, and run both upstream and consumer tests. Otherwise,
   explicitly state that target execution was not performed.

## Validated Example

libsigc 2.12.1 on 2026-07-19:

- Meson completed 103/103 build steps and compiled 32 upstream test targets;
- the shared package and a real signal/slot consumer linked successfully;
- the package contained AArch64 `libsigc-2.0.so` with SONAME
  `libsigc-2.0.so.0`;
- all 32 upstream tests and the real Conan consumer were signed in place and
  executed on a HarmonyOS PC AArch64 device on 2026-07-24; all 33 returned 0.
