# E213: `CLOCK_SGI_CYCLE` declared but unsupported at runtime


## Symptom

An upstream FFTW CTest entry such as `bench -s 32x64` remains in the default
`FFTW_MEASURE` planning phase until an outer timeout terminates it. The same
binary finishes quickly when `-oestimate` is added, but that option changes the
official test semantics and is only diagnostic evidence.

## Root Cause

The target libc headers define `CLOCK_SGI_CYCLE`, so FFTW 3.3.10 selects the
SGI cycle-clock branch in `kernel/cycle.h`. At runtime,
`clock_gettime(CLOCK_SGI_CYCLE, ...)` returns `-1` with `EINVAL`. FFTW does not
check this return value. Invalid timing samples reach `measure_execution_time()`
and can repeatedly take its `start_over` path.

## Fix

Check the return value from `clock_gettime(CLOCK_SGI_CYCLE, ...)` and fall back
to `CLOCK_MONOTONIC` only when the requested clock is unsupported. Platforms
with a working SGI cycle clock retain the upstream path. This preserves measured
planning, avoids platform-name conditionals, and leaves the upstream test command
line unchanged.

## Validation

1. Confirm `CLOCK_SGI_CYCLE` is declared but returns `-1/EINVAL`.
2. Confirm `CLOCK_MONOTONIC` returns success.
3. Rebuild and inspect the generated timer code.
4. Run the unchanged official entries `bench -s 32x64` and `bench -s ib256`.
5. Require both CTest results to pass and retain the raw logs and input hashes.
