# E264: Bridge legacy *-config probes with a metadata-derived signed ELF adapter

> **Contributor**: 2301_80739235 | **Status**: Verified | **Updated**: 2026-08-08
> **Severity**: 2 | **Category**: dependency-discovery / autotools / conan / hmdfs / elf-signing

## Symptom

A dependency resolves successfully in Conan and exposes valid include,
library, link, and version metadata, but the consumer's `configure` script
still insists on executing a legacy helper such as `geos-config`.

## Root Cause

Legacy configure logic treats `*-config` as an executable protocol. Modern
packages increasingly export CMake targets or pkg-config data instead, so a
Conan package can be semantically complete while lacking the executable that
the older consumer expects.

Two tempting substitutes are not portable:

1. A shell shim retains the direct-script-execution failure on HMDFS.
2. Hard-coded cache paths are detached from the dependency revision.

## Solution

Generate a minimal C helper in the build folder from the resolved dependency
`cpp_info` values:

1. Read required values from `self.dependencies["<name>"].cpp_info`.
2. Fail if required include or library directories are absent.
3. Generate a minimal C program implementing only the query switches used by upstream.
4. Compile with the active C compiler.
5. Sign the resulting ELF when the executor requires signed binaries.
6. Pass the helper's absolute path through `--with-<name>config=<path>`.

## Forbidden Shortcuts

- Do not hard-code cache or device paths.
- Do not generate a shell script when direct script execution is the failing capability.
- Do not return success for unknown switches.

## Verification

The pattern was implemented for `librttopo/1.1.0.1` and reused by
`libspatialite/5.1.0.1`, both against the exact `geos/3.13.1` Conan metadata.
