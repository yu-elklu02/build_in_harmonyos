# E298 - Conan test_package 的显式运行与环境

## 使用说明

当 Conan `test_package` 已成功编译消费者，但 `cmake.test()`/CTest 在执行阶段失败时使用本条目。它提供“先取具体错误、再决定是否启用 Conan runenv”的分诊边界，不把所有 CTest 失败都归因于运行环境。

## 适用范围

- Conan 2 `test_package` 使用 CMake 构建消费者。
- 消费者链接包内共享库，或需要执行包内 CLI。
- 包的运行依赖通过 Conan `VirtualRunEnv` 提供，例如 `PATH`、动态库搜索路径或其他运行时变量。

## 输入定义

- 被测 Conan 包和 `test_package`。
- 消费者可执行文件路径。
- 需要从包目录解析的共享库、CLI 或运行时资源。

## 输出定义

- `test()` 中可审计的显式 `self.run()` 命令。
- 通过 `env="conanrun"` 激活的 Conan 运行环境。
- API/CLI 业务断言和 L1e 破坏性反向验证均能证明测试真实依赖被测包。

## 错误特征

```text
Test #1: test_package ...***Failed
Errors while running CTest
ERROR: pkg (test package): Error in test() method
    cmake.test()
```

如果 CTest 没有使用 `--output-on-failure`，日志可能只显示测试失败，不显示动态加载器的具体错误。仅有通用的 `Errors while running CTest` 还不足以判断根因，必须先读取 `LastTest.log` 或显式运行消费者。

## 根因

`CMake.test()` 启动 CTest 子进程，但不会替代 Conan 运行环境的生成与显式激活。消费者若链接包内 `.so` 或调用包内 CLI，测试进程可能找不到动态库或命令。即使根因不是动态加载，隐式 CTest 入口也不利于 CI 确认执行了哪个消费者、使用了什么工作目录和环境。

只有具体错误包含 `Error loading shared library`、`cannot open shared object file`、`shared library not found` 或包内命令找不到时，才进入 `VirtualRunEnv` 分支。断言失败、崩溃、权限和业务输出错误应继续按各自根因处理。

## 解决步骤

1. 先用 `ctest --output-on-failure` 或 `LastTest.log` 确认执行期错误，不把所有 CTest 失败都归因于运行环境。
2. 在 `test_package` 中加入 `VirtualRunEnv`。
3. CMake 只负责配置和构建消费者。
4. 在 `test()` 中解析消费者的准确路径并显式调用 `self.run(..., env="conanrun")`。
5. 测试包内 CLI 时，从 `self.dependencies["pkg"].package_folder` 取得路径。
6. 检查业务输出，不要只检查退出码。

```python
import os

from conan import ConanFile


class TestPackage(ConanFile):
    generators = "CMakeDeps", "CMakeToolchain", "VirtualRunEnv"

    def test(self):
        test_bin = os.path.join(self.cpp.build.bindirs[0], "test_package")
        self.run(f'"{test_bin}"', env="conanrun", cwd=self.build_folder)

        tool = os.path.join(
            self.dependencies["pkg"].package_folder, "bin", "pkg-tool"
        )
        self.run(f'"{tool}" --version', env="conanrun")
```

## 禁止做法

- 消费者需要共享库或包内 CLI 时只调用 `cmake.test()`。
- 为让测试通过而硬编码开发机的 `LD_LIBRARY_PATH` 或包缓存路径。
- 只打印固定字符串，不调用被测 API、不执行包内命令。
- 只依据测试退出码，不验证输出语义。

## 验证证据

PR #2063 `mcpp/2.7.2` 的 CI #2228 已成功构建消费者，但 `cmake.test()` 执行的 CTest 为 0/1 通过。日志只保留了 `LastTest.log` 路径，没有具体测试输出，因此该事件只能触发分诊，不能单独证明缺少 `conanrun` 是根因。

后续组合修复同时调整了静态/共享策略、测试源码、CTest 入口、`VirtualRunEnv`、显式 `self.run()` 和 API/CLI 断言。CI #3530 的 L0/L1/L1e 均通过，Build Summary 为 1/1；这证明最终模式可用，但不构成 `conanrun` 的单变量 A/B 证明。

## 关联条目

- R34：`test_package` 必须实质依赖被测包。
- CI L1e：移走 `bin/`、`lib/`、`include/` 后确认测试确实会失败。
- E019：一般 Linux 共享库搜索路径问题。
- E088：HarmonyOS musl namespace 忽略运行路径；`VirtualRunEnv` 可能无效。
- E212：hmmac 安全标签导致 `.so` 加载被拒；runenv 不能绕过安全标签或签名限制。
