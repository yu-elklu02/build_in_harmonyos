# E320: HarmonyOS fmemopen 符号存在但运行时不可用，AC_CHECK_FUNCS 误判，需 AC_RUN_IFELSE 运行时探测并回退临时文件

> **Contributor**: 1E7B | **Status**: DRAFT | **Created**: 2026-08-11
> **Severity**: medium | **Category**: platform|libc|autotools|runtime-probe

## 错误特征

HarmonyOS libc 导出 `fmemopen` 符号且链接成功，但运行时对缓冲区写入无效，`fclose` 返回 `EBADF`（bad file descriptor）。上游 autotools 项目用 `AC_CHECK_FUNCS([fmemopen])` 做链接级检测时误判 `HAVE_FMEMOPEN=1`，源码走 `fmemopen` 内存流路径，导致：

- 输出内容损坏或为空；
- `fclose(fp)` 返回 `EBADF`；
- 依赖该缓冲内容的消费者函数（如 `cob_get_field_str`）读到截断或未初始化数据。

真实日志症状（gnucobol 3.2）：

```text
checking for fmemopen... yes            # AC_CHECK_FUNCS 链接级误判
...
fclose(fp) -> EBADF                     # 运行时不可用
```

## 触发条件

1. 目标平台为 HarmonyOS/OHOS（交叉编译，configure 无法运行宿主探测程序）。
2. 上游使用 `AC_CHECK_FUNCS` 检测 `fmemopen`（仅链接检查）。
3. 运行时实际调用 `fmemopen` 写缓冲并 `fclose`。

## 根因分析

`AC_CHECK_FUNCS` 只验证符号可链接，不验证语义可用。HarmonyOS 的 `fmemopen` 符号存在但内存流写入/关闭行为不满足 POSIX 契约（`fclose` 返回 `EBADF`），因此"链接成功"与"可用"不等价。修复必须把检测从链接级升级为运行时级：用 `AC_RUN_IFELSE` 真实写读缓冲探测，仅在探测通过时定义 `HAVE_FMEMOPEN`；失败时源码回退临时文件实现。

## 修复方案（推荐）

在 `configure.ac` 中移除 `AC_CHECK_FUNCS` 列表中的 `fmemopen`，改用 `AC_RUN_IFELSE` 运行时探测并缓存结果：

```m4
AC_CACHE_CHECK([whether fmemopen works], [ac_cv_fmemopen_works],
  [AC_RUN_IFELSE(
    [AC_LANG_PROGRAM(
      [[#include <stdio.h>
        #include <string.h>]],
      [[char buf[32];
        FILE *f = fmemopen(buf, sizeof(buf), "w");
        if (!f) return 1;
        if (fprintf(f, "test") != 4) { fclose(f); return 1; }
        fclose(f);
        return strcmp(buf, "test") != 0;]])],
    [ac_cv_fmemopen_works=yes],
    [ac_cv_fmemopen_works=no],
    [ac_cv_fmemopen_works=no])]
)
if test "$ac_cv_fmemopen_works" = yes; then
  AC_DEFINE([HAVE_FMEMOPEN], [1], [Define if fmemopen works properly])
fi
```

对应补丁（gnucobol 3.2）：

- `patches/0006-configure-ac-fmemopen.patch` — configure.ac 运行时探测；
- `patches/0007-configure-fmemopen.patch` — 生成版 configure 的对应修改；
- `patches/0004-libcob-call.c.patch` — 源码回退临时文件（`cob_create_tmpfile`），并将回退读取量限制为 `size-1`、检查 `fseek`、按实际 `fread` 字节数写 NUL，防止短缓冲区越界。

## 回退方案

当运行时探测失败（或无法运行探测程序）时，源码回退到不可预测命名的临时文件实现，并对回退读取路径做边界防护（限制读取长度、检查 fseek、按实读字节写 NUL）。

## 验证命令

```bash
grep -n "ac_cv_fmemopen_works" configure          # 运行时探测结果缓存存在
grep -n "AC_RUN_IFELSE" configure.ac              # 探测宏存在
grep -n "HAVE_FMEMOPEN" libcob/call.c             # 仅在探测通过时启用 fmemopen 路径
make MAKEINFO=true check -j1                      # 上游测试全量
```

## 真实证据（gnucobol 3.2, 2026-08-11）

- `make check` 上游 testsuite：**TOTAL=1282、PASS=1226、SKIP=56、FAIL=0**（56 项为显式禁用可选功能的上游正常 SKIP，未计入 PASS）。
- 修复前：`patch stream is incomplete!` / `ConanException: Failed to parse patch`（0006 hunk 行数声明错误）；修复后七补丁在全新源码树依序验证可应用。
- 消费者验证：`cob_get_field_str` 短缓冲区（8 字节）边界测试通过，尾部哨兵完整。

## 禁止

- 禁止仅凭 `AC_CHECK_FUNCS` 链接检测定义 `HAVE_FMEMOPEN`（会把坏路径编进制品）。
- 禁止在源码/补丁中引入 `#ifdef __OHOS__` 平台宏（R8 违规；平台差异应通过 configure 运行时探测表达）。
